# Query performance and indexing

Member 10. Tested on the sample data from `sp_generate_sample_data(50000)`: 50,000 orders, about
75,000 order items and 50,000 payments.

## How we tested

We picked four questions the reports ask often, and ran each one twice with `EXPLAIN` (the plan
MySQL chooses) and `EXPLAIN ANALYZE` (the real run time). We ran the whole file once to warm up
MySQL's memory and kept the second run, so the before and after numbers are compared fairly.
Then we added the indexes in `V1002__report_indexes.sql` and ran exactly the same file again.

The test file is `database/queries/member10-index-tests.sql`. The full outputs are in
`docs/performance/before.txt` and `docs/performance/after.txt`.

## The four queries and their indexes

| # | Question | Index added | Why it helps |
|---|---|---|---|
| 1 | A customer's history, found by phone number | `idx_users_phone (phone)` | Without it, MySQL reads every user to find one phone number. With it, MySQL jumps straight to the matching row. |
| 2 | Completed sales per month, last 12 months | `idx_orders_status_created_total (status, created_at, total_amount)` | Composite and covering. `status` is matched exactly, then `created_at` as a range, and `total_amount` is already in the index, so MySQL never opens the order rows. |
| 3 | Payments waiting for confirmation | `idx_payments_status (status)` | Only a small share of payments are pending. The index finds just those instead of reading all of them. |
| 4 | Top 10 best sellers | `idx_order_items_product_cover (product_id, quantity, unit_price)` | Covering: everything the sum needs is in the index, so MySQL reads the smaller index instead of the whole table. |

We also **dropped** the old `idx_order_items_product (product_id)`. The new index starts with
`product_id`, so it already serves the foreign key and the old one only cost extra disk space and
slower inserts.

## How to read the plans

- `type`: **ALL** means a full table scan. **ref** means an index lookup. **range** means an index range. **index** means the whole index is read, which is still smaller than the table.
- `key`: the index MySQL used (NULL means none).
- `rows`: how many rows MySQL expects to read.
- `Extra`: **Using index** means the query was answered from the index alone (a covering index).
- `actual time=a..b`: `b` is the time in milliseconds until the last row.

## Trade-offs

Indexes make reads faster but every insert and update has to maintain them too. We only added
indexes for questions the reports actually ask, and removed the one that became redundant. For a
shop like this, which reads reports far more often than it writes thousands of orders at once,
that trade is worth it.
